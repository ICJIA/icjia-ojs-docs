A test drive of Open Journal Systems

Open Journal Systems (OJS) is free software for running a research journal: it collects submissions, routes them to reviewers, tracks edits, and publishes the finished articles online. Tens of thousands of journals around the world use it.

The question we're answering: would OJS be a good way for ICJIA to publish its research? We're setting up a small working copy so staff can see it for themselves before anyone commits to anything.

2

3

Without a system like this, journal work runs on email threads, shared folders, and people remembering who has what. OJS puts all of it in one place with a record of every step.

This server is not permanent. This is a proof-of-concept test.

Published research carries a DOI, a permanent identifier that libraries, citations, and search engines rely on forever. A DOI cannot be recalled once issued.

If anything were published from this test server, the world would point to a temporary address on a machine we intend to delete. No DOIs will be issued, and nothing will be indexed or announced, until a production system exists.

Nothing on the test server is real, published, or permanent.

What a DOI is, and why we're careful with them

10.12345/icjia.2026.001

A DOI, or Digital Object Identifier, is a permanent ID for a published article. The first part identifies the publisher; the second identifies the article. Anyone, anywhere, can type it into doi.org and land on the article, no matter where the article lives.

The problem it solves

Web addresses break. Sites get redesigned, moved, or shut down, and every citation pointing at the old link dies.

A DOI separates what an article is from where it currently sits. Move the article, update one record, and every citation ever written still works.

Why research depends on it

Google Scholar, citation counts, reference managers, and library catalogs all key on the DOI. Many journals require DOIs in reference lists. Funders and indexes treat DOI assignment as the mark of a real journal.

For ICJIA it's how our research gets found, cited, and counted.

Why it can't be undone

Issuing a DOI is a promise to keep it working forever. It's registered with a nonprofit called Crossref under the publisher's name. You can update where it points; you can never delete it.

A DOI issued from a test server would point at a machine we plan to erase, with ICJIA's name attached.

How OJS handles DOIs

  1. ICJIA joins Crossref (the nonprofit that runs the DOI registry) and receives a publisher prefix. At ICJIA's size, membership is a few hundred dollars a year.
  2. An editor turns on DOIs in the journal settings and picks a naming pattern.
  3. OJS generates a DOI for each article automatically. At this point it exists only inside our system.
  4. OJS sends the article's details to Crossref, and the DOI becomes real and permanent. This step will not be turned on during the test.
  5. The DOI appears on the article page. If the site ever moves, one update to Crossref redirects every citation to the new address.

Steps 1 through 3 are safe to explore. Step 4 requires a Crossref account and credentials that the test server simply won't have, so nothing can be registered by accident. For the same reason, the test won't be submitted to Google Scholar, DOAJ, or any other index.

Who does what on the test server

Once OJS is installed, nearly all the work is in the browser. The journal administrator in R&A runs the journal; IDS keeps the machine running. Here is the full list of what needs a technical person, and roughly how much time it takes.

R&A administrator

  • Creates the journal and sets it up
  • Adds users and assigns roles
  • Runs submissions, reviews, and decisions
  • Edits email templates, themes, pages
  • Adds features from OJS's built-in add-on gallery
  • Builds and publishes issues

All of it, from a web browser

IDS

  • Keeps the server patched and running
  • Upgrades OJS when new versions ship
  • Runs and tests backups
  • Fixes the rare "site is down" problem
  • Rebuilds the server if it's ever wrecked

Quickstart for the OJS administrator

IDS installed the software and entered the database details. Everything from here happens in a web browser, using the admin login IDS hands you. Work top to bottom.

  1. 1

    Log in and secure the admin account

    Go to ojs.icjia.cloud and sign in with the username and password from IDS. First thing: top-right menu → Edit Profile → Password and set your own. Then Profile → Contact and make sure the email is one you read; OJS sends everything there.

  2. 2

    Create the journal

    A fresh OJS site has no journals. Administration → Hosted Journals → Create Journal. Give it a title, a short web path (this becomes part of every link, so keep it short and never change it), and a language. Everything else can be filled in later.

    OJS then opens the journal's Settings wizard. Fill in Masthead (title, description) and Contact (principal contact is you; technical contact is IDS). Skip the rest for now.

    Leave off during the test: Settings → Distribution → DOIs, and anything labeled indexing or search-engine registration. See the DOI section above.
  3. 3

    Learn the roles before adding people

    RoleWhat they can doWho gets it
    Site AdministratorEverything, on every journal.You, plus one backup.
    Journal ManagerAll settings, users, and workflow for one journal.Whoever runs the journal day to day.
    EditorSees every submission; assigns reviewers; decides.Editor-in-chief.
    Section EditorSame, but only for submissions assigned to them.Associate editors.
    ReviewerSees only what they're invited to review.Anyone who reviews.
    AuthorSubmits and tracks their own manuscripts.Anyone who submits.

    One person can hold several roles. For a small shop, one Manager who is also Editor, plus a few Reviewers, is a complete journal.

  4. 4

    Add users

    Inside the journal: Users & Roles → Users → Add User. Name, username, email, a temporary password, and tick Send the user a welcome email so they get their login (this also proves email works). Assign roles on the same form. To change roles later, click the person's name → Edit User.

  5. 5

    Make a second site administrator

    One admin with a forgotten password is the most common OJS problem there is. Create a second account as in step 4, then edit it and look for Site Administrator in the roles list. If it's there, tick it and tell IDS the username. If the list only shows journal roles, file a Freshservice ticket and IDS will grant it.

  6. 6

    Run one fake article all the way through

    This is the real test. Make yourself a second account as an Author (different email), submit a fake manuscript, then as Editor: assign a Reviewer (a third account), complete the review as that reviewer, record a decision, copyedit, build an issue, publish. Every step sends an email; watch them arrive.

    By the end you'll know whether the workflow fits how R&A actually works. That's the question this whole exercise exists to answer.

Expectations: try it first, or file a ticket?

Most questions about OJS are questions about a setting, not about the server. This is how to tell the difference.

Try it first

The administrator handles these. Most take five minutes.

  • "How do I make OJS do X?" It's almost always a setting. Look in Settings, then search the PKP forum (forum.pkp.sfu.ca) or the OJS user guide. Someone has asked already.
  • A user can't log in. Use the "forgot password" link, or reset their password from Users & Roles.
  • Someone can't see a submission. Check their role; reviewers and section editors only see what's assigned to them.
  • An email went out with the wrong wording. Email templates are editable under Settings → Workflow → Emails.
  • The site looks wrong. Theme and appearance settings are under Settings → Website.
  • A feature seems to be missing. Many are add-ons ("plugins") you can switch on yourself under Settings → Website → Plugins → Plugin Gallery.

File a ticket

These need IDS. Nothing in the browser will fix them.

  • The site is down or shows a blank page or an error message instead of OJS. (Check uptime.icjia.app first; it may already know.)
  • No email is sending at all, for anyone, after you've done the quick email check below.
  • Uploads are rejected for being too large, when the file is a normal size.
  • A new OJS version is out and you want it, or the site says it needs upgrading.
  • You need a second site administrator and the role isn't offered in the user form.
  • Something needs to change on the web address, its security certificate, or the email setup.
  • You've broken it and want it restored from backup. It happens; that's what a test server is for.

The rule of thumb: if the fix is in a Settings menu, it's yours. If the fix needs someone to log in to the server itself, it's a Freshservice ticket. When in doubt, spend ten minutes looking before filing.

Quick email check (do this before filing)

  • Log out, click Forgot your password? on the login page, enter your admin email, and wait.
  • Give it up to 15 minutes. Some mail arrives fast; some doesn't. Don't file at minute two.
  • Check spam and junk. The state's mail system (DoIT) tags anything from outside as [EXTERNAL], and OJS mail counts as outside. It's often filtered.
  • If it never arrives, the ticket should say so. IDS can check Mailgun's logs, which show whether the message left our system successfully. Mailgun keeps only 5 days of logs, so report promptly.
  • A message that Mailgun shows as delivered can still be held or dropped on DoIT's side. That's a DoIT question, not an OJS one; IDS will route it.

Tickets go in Freshservice. A useful one includes:

  • What you were trying to do, and which screen you were on
  • What happened instead, with the exact wording of any error
  • Whether it affects one person or everyone
  • When it started, and whether anything changed right before
  • A screenshot if there's anything to see

Two things IDS asks of R&A

Name a backup admin

OJS lives or dies by its admin account. If the main administrator leaves, changes roles, or is out for a month, someone else must already be able to log in with full rights.

At least one backup admin, two is better. A backup admin is a second person with a full site-administrator login who can run OJS if the main admin is unavailable. Create them early (see step 5 of the Quickstart), and tell IDS who they are. If the main admin's departure is planned, hand over before they go, not after.

R&A owns succession; IDS needs the names

Tell IDS the moment the answer is no

If R&A decides OJS isn't the right fit, that's a perfectly good outcome of a test. But the server keeps billing every month it exists, and there is nothing on it worth keeping.

Send IDS a note the same day. The server will be shut down and deleted, and the cost stops. No approvals, no paperwork; a one-line email is enough.

Decision made → IDS notified → server gone

Turnaround on the test server is best-effort; it isn't a production system and nothing on it is urgent. A live server would come with a real support agreement, and that's part of the "if we adopt it" conversation.

If we decide to adopt it

Five things would need to happen before OJS could host a real journal. None are blockers, and each has a clear owner.

A bigger server

The test machine is deliberately tiny. A real journal needs more room. On-premise is preferred, run by someone in R&A or IDS with remote access. AWS is a workable alternative; Karl G. has run one there.

A live journal is an archive of record: it needs enterprise-grade backups with frequent incremental copies, off-site storage, and, most importantly, regular test restores so we know the backups actually work before we ever need them.
