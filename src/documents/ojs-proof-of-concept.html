A test drive of Open Journal Systems

Open Journal Systems (OJS) is free software for running a research journal: it collects submissions, routes them to reviewers, tracks edits, and publishes the finished articles online. Tens of thousands of journals around the world use it.

The question we're answering: would OJS be a good way for ICJIA to publish its research? We're setting up a small working copy so staff can see it for themselves before anyone commits to anything.

2

Editors assign reviewers. Everyone sees deadlines and status on one screen.

3

Revisions, copyedits, and layout happen in one place with a full history.

4

Publish

Articles go live on a public website, organized by issue, searchable and citable.

Without a system like this, journal work runs on email threads, shared folders, and people remembering who has what. OJS puts all of it in one place with a record of every step.

This server is not permanent. This is a proof-of-concept test.

Published research carries a DOI, a permanent identifier that libraries, citations, and search engines rely on forever. A DOI cannot be recalled once issued.

If anything were published from this test server, the world would point to a temporary address on a machine we intend to delete. No DOIs will be issued, and nothing will be indexed or announced, until a production system exists.

Nothing on the test server is real, published, or permanent.

What a DOI is, and why we're careful with them

10.12345/icjia.2026.001

A DOI, or Digital Object Identifier, is a permanent ID for a published article. The first part identifies the publisher; the second identifies the article. Anyone, anywhere, can type it into doi.org and land on the article, no matter where the article lives.

The problem it solves

Web addresses break. Sites get redesigned, moved, or shut down, and every citation pointing at the old link dies.

A DOI separates what an article is from where it currently sits. Move the article, update one record, and every citation ever written still works.

Why research depends on it

Google Scholar, citation counts, reference managers, and library catalogs all key on the DOI. Many journals require DOIs in reference lists. Funders and indexes treat DOI assignment as the mark of a real journal.

For ICJIA it's how our research gets found, cited, and counted.

Why it can't be undone

Issuing a DOI is a promise to keep it working forever. It's registered with a nonprofit called Crossref under the publisher's name. You can update where it points; you can never delete it.

A DOI issued from a test server would point at a machine we plan to erase, with ICJIA's name attached.

How OJS handles DOIs

  1. ICJIA joins Crossref (the nonprofit that runs the DOI registry) and receives a publisher prefix. At ICJIA's size, membership is a few hundred dollars a year.
  2. An editor turns on DOIs in the journal settings and picks a naming pattern.
  3. OJS generates a DOI for each article automatically. At this point it exists only inside our system.
  4. OJS sends the article's details to Crossref, and the DOI becomes real and permanent. This step will not be turned on during the test.
  5. The DOI appears on the article page. If the site ever moves, one update to Crossref redirects every citation to the new address.

Steps 1 through 3 are safe to explore. Step 4 requires a Crossref account and credentials that the test server simply won't have, so nothing can be registered by accident. For the same reason, the test won't be submitted to Google Scholar, DOAJ, or any other index.

Why this is low risk

No licence to buy

OJS is open source. The test server costs a few dollars a month and can be switched off any time. Production is not free — see what it would actually cost, below.

Nothing to lose

The test lives at a temporary address (ojs.icjia.cloud) with made-up content. Nothing is published, indexed, or permanent.

Well-trodden ground

OJS has been in development since 2001 and runs on ordinary web hosting, the same kind IDS already manages for ICJIA's other sites.

Same hands

The test is being built by IDS, which already runs 15+ ICJIA web properties. This is a smaller job than most of them.

Who does what on the test server

Once OJS is installed, nearly all the work is in the browser. The journal administrator in R&A runs the journal; IDS keeps the machine running. Here is the full list of what needs a technical person, and roughly how much time it takes.

R&A administrator

  • Creates the journal and sets it up
  • Adds users and assigns roles
  • Runs submissions, reviews, and decisions
  • Edits email templates, themes, pages
  • Adds features from OJS's built-in add-on gallery
  • Builds and publishes issues

All of it, from a web browser

IDS

  • Keeps the server patched and running
  • Upgrades OJS when new versions ship
  • Runs and tests backups
  • Fixes the rare "site is down" problem
  • Rebuilds the server if it's ever wrecked

Who runs it, day to day

Once OJS is installed, running the journal is a browser job: creating it, adding people, moving submissions through review, building issues, publishing. None of it needs server access, and the administrator will not be given any.

That work has its own guide so this page can stay about the decision: Running the journal — a guide for the OJS administrator. It covers first login, creating the journal, the roles, adding people, naming a backup administrator, and the one end-to-end test that answers whether OJS fits how R&A works. It also draws the line between what the administrator fixes and what needs a ticket.

Two things IDS asks of R&A. Name a backup administrator early — one admin with a forgotten password is the most common OJS problem there is, and R&A owns that succession. And if the answer turns out to be no, say so the same day: the server bills every month it exists and there is nothing on it worth keeping. A one-line email is enough; no approvals, no paperwork.

If we decide to adopt it

Five things would need to happen before OJS could host a real journal. None are blockers, and each has a clear owner.

A bigger server

The test machine is deliberately tiny. A real journal needs more room. On-premise is preferred, run by someone in R&A or IDS with remote access. AWS is a workable alternative; Karl, a former R&A center manager, has run one there.

What it would actually cost. The software stays free, but a real journal is not a $0 line item. Budget for a production server sized for the load, a Crossref membership if DOIs are wanted (a few hundred dollars a year at ICJIA's size), the Laravel Forge subscription if the server is managed that way, and IDS time for upgrades and backup testing. None of these is large, and none is a surprise — but “free software” and “free to run” are different claims, and only the first one is true.

A verified backup and restore plan

The test server gets a full weekly backup from the hosting provider, which is fine for a throwaway. A live journal is an archive of record: it needs enterprise-grade backups with frequent incremental copies, off-site storage, and, most importantly, regular test restores so we know the backups actually work before we ever need them.
