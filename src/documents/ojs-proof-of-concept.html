A test drive of Open Journal Systems

Open Journal Systems (OJS) is free software for running a research journal: it collects submissions, routes them to reviewers, tracks edits, and publishes the finished articles online. Tens of thousands of journals around the world use it.

The question we're answering: would OJS be a good way for ICJIA to publish its research? We're setting up a small working copy so staff can see it for themselves before anyone commits to anything.

TL;DR — the short version

Six lines. Everything after this is the supporting detail, to be read only if you want it.

  • What this is. A working test copy of OJS — free software for running a peer-reviewed journal — set up at a temporary address so staff can see it before anyone commits to anything.
  • Where it stands. Five of seven steps done: installed, secured, and sending email. Nothing real is published, no DOIs are registered, and the server gets erased at the end.
  • It is not a replacement for the Research Hub. OJS is a journal expressed as software. The Hub publishes articles, datasets, and dashboards, and is the most-read part of ICJIA's website — 60% of all visitors. Replacing it would move roughly 540 web addresses and give up years of search standing.
  • But it could be genuinely useful alongside it — say, as a quarterly. The Hub keeps publishing articles as they are finished; four times a year a selection is gathered into a peer-reviewed issue with an ISSN and a DOI on every paper. The same issue-based design that makes OJS a poor replacement is what makes it a good addition.
  • Or the Studio could be built out instead. Reviewers, rounds, and deadlines are additions to something that already exists. Issuing DOIs is not — that is a permanent commitment to Crossref no matter who builds it.
  • The actual decision is not which tool. It is whether ICJIA wants to publish a peer-reviewed journal — which would raise the standing of research the agency already produces. The software is the easy part; an editorial board, reviewers willing to work for free, and a steady stream of submissions are not.

Nothing has been committed, and nothing on the test server can be made permanent by accident.

What OJS does

1

Submit

An author uploads a manuscript through a web form. No email attachments, no lost drafts.

2

Review

Editors assign reviewers. Everyone sees deadlines and status on one screen.

3

Edit

Revisions, copyedits, and layout happen in one place with a full history.

4

Publish

Articles go live on a public website, organized by issue, searchable and citable.

Without a system like this, journal work runs on email threads, shared folders, and people remembering who has what. OJS puts all of it in one place with a record of every step.

How this relates to the Research Hub

ICJIA already publishes research, through the Research Hub and the Studio behind it. So the fair question about OJS isn't whether it's good software — it is — but what it would actually do for R&A that the current setup doesn't. Three versions of that question are worth separating: could OJS replace the Hub and Studio, could it run alongside them, or could the Studio be built out to do the same job? What follows answers each, including where the current setup falls short.

The Hub

The public site at icjia.illinois.gov/researchhub, running since 2019. It publishes articles, datasets, and interactive dashboards.

It is the most-read part of ICJIA's website — 47% of all pages read and 60% of all visitors over the past year. Eight of the twelve most-visited pages on the whole site are Hub articles.

Said honestly: the software that stores its content stopped getting security updates in 2022.

The Studio

The staff tool behind the Hub. R&A writers work in a plain-language editor, see the page exactly as it will appear, attach files, and save a draft.

Work moves created → submitted → published. A manager looks at what's waiting and publishes it. The public Hub has no editing features at all; every change starts in the Studio.

Said honestly: review is a single step — one approval, with no reviewer comments kept on the record.

Hub 2.0

A rebuild of both, on a current content system — built and working, but not published, still under review and consideration, much like this test. Working drafts are up for internal review: the public site and the new Studio (choose “editor”; no password needed).

Internally the work is codenamed “Copperhead”, which is why that word appears on the drafts. Readers never see it: at launch it simply becomes the Research Hub again, same name, same web addresses.

This proof-of-concept doesn't affect it either way.

Where the two are the same

  • Both split the work the same way: a private tool for writing and editing, a separate public site for reading.
  • Both put a draft in front of an editor before anything goes live.
  • Both keep track of authors, summaries, topics, and attached files, and both let a writer see the finished page before it goes out.
  • Both produce a public, searchable library of ICJIA research that stays put and can be cited.

The shape is the same. The difference is what happens in the middle step — and what comes out the other end.

What the Hub has already earned

Before weighing any change, it's worth being clear about what the current setup is worth. These are live figures for icjia.illinois.gov over the past twelve months.

Three things stand out, and all three are about being found:

  • Eight of the ten pages people most often arrive on are Hub articles. Only the homepage draws more, and the five after it are all Hub articles. Readers don't come through the front door and browse — they land on an article straight from a search.
  • The Hub earns nearly all of the agency's search traffic. Google sends 25,500 visitors a year to the whole site; 21,500 of them come to the Hub. It is the Hub's single largest source, ahead of everything else.
  • They stay. A Hub visit averages just over fifteen minutes, against ten for the site as a whole. People arrive and actually read.

That standing took years to build, and it is attached to the web addresses themselves, not to the writing on them. Google ranks a page at an address. Move an article to a new address and, as far as a search engine is concerned, it is a new page: it has to be found again, judged again, and climb again — a process measured in months. Every link, bookmark, syllabus, and citation pointing at the old address is affected at the same time.

Could OJS replace the Hub and Studio outright?

No

OJS is not a general publishing tool that happens to suit journals. It is a journal, expressed as software. That assumption runs all the way down, and it is the most important thing to understand about it:

  • You have to create a journal before you can create anything else. There is no neutral starting point. OJS asks you to set up a journal site first, and everything afterwards hangs off it.
  • Content is filed into issues and sections. Articles go into volumes and numbers, and within those into sections — Articles, Reviews, Editorials. That is the filing cabinet, and there isn't a second one.
  • People are given journal roles — Journal Manager, Editor, Section Editor, Reviewer, Author — and what each person can do follows from the role they hold.
  • The finish line is an issue. The whole pipeline is built to end in a table of contents, with DOIs assigned and the issue's details sent out to indexes. It is designed to produce a periodical, on a schedule.

Set that against what the Hub publishes: articles, datasets, and interactive dashboards, with centers, projects, and staff pages around them, each going up when it is ready. In OJS a dataset lives as a file attached to an article. To be fair to it, that file can carry its own DOI and be cited in its own right — a genuine strength — but it still cannot stand as an entry of its own the way it does on the Hub. A dashboard has nowhere to live at all, and nothing publishes without an issue to publish into.

Then there is the cost of moving:

  • Every web address would change. OJS builds its own address structure, so all of the Hub's roughly 540 pages would move. Forwarding old addresses to new ones carries some of the search standing across, but only if every single one is mapped correctly and kept that way permanently — and the climb back still takes months. Set against the figures above, this is the most expensive item on this page.

Replacement would trade two of the Hub's three kinds of content, the site's whole structure, and its hard-won search standing for a review workflow — and would require ICJIA to describe all of its research as a periodical, which it isn't. That trade isn't worth making, and nothing in this test proposes it.

But read that list again with fresh eyes, because every one of those traits is a mismatch only against the Hub. Judged on its own terms, a system built to assemble reviewed work into issues on a schedule is not a limitation at all — it is a description of a journal, which is the next question.

If a journal isn't the shape, what is?

Worth a moment, because it clarifies what OJS is actually for. The nonprofit behind OJS — the Public Knowledge Project — hit this same limit themselves, and answered it by building sister tools that share the same underlying workflow, each shaped for a different kind of output:

  • OPS (Open Preprint Systems) — for posting research promptly, without formal peer review and without waiting for an issue to be assembled. Of the three, the closest to how the Hub already works.
  • OMP (Open Monograph Press) — for books, edited volumes, and monographs.

And for a broad collection of independent papers and institutional output — a library of what an agency has produced, rather than a periodical — the category built for that job is repository software such as DSpace or Invenio. That is the shelf the Hub currently occupies, in a form built for ICJIA's own readers.

None of these is being proposed here. The point is narrower, and worth stating plainly: OJS is the industry standard for running a peer-reviewed periodical, and that is the one job it should be judged on. Choosing it means choosing to publish a journal.

Could OJS run alongside, as an addition?

Yes — and this is the possibility worth taking seriously

Here is the turn. The very thing that rules OJS out as a replacement — that it is built to produce a periodical, in issues, on a schedule — is precisely what would make it worth having as an addition.

The Hub already does the thing OJS does poorly: publishing individual articles, continuously, each one as it is finished. It should carry on doing exactly that. What the Hub does not do, and cannot easily be made to do, is gather that work into a formal, peer-reviewed volume that the scholarly world recognizes as such.

So picture a quarterly. Nothing about the Hub changes:

  • Research keeps appearing on the Hub as it always has — article by article, as each is ready, reaching the readers it already reaches.
  • Four times a year, a selection is assembled into a reviewed issue of an ICJIA journal: an editorial board, outside reviewers, an ISSN (the standard number identifying a periodical, as an ISBN identifies a book), and a DOI on every article.
  • The two are not rivals. The Studio already has a box for a DOI, so the Hub can list the article carrying the identifier the journal issued. A reader finds the work either way, and the citation points somewhere permanent. Nothing new has to be built for that; the box is already there.

Why this could genuinely matter to R&A. Hub articles are widely read — the figures above make that plain — but they are not peer-reviewed, carry no DOI, and are largely invisible to Google Scholar, citation counts, and library catalogues. That is a real ceiling on work the agency has already paid to produce. A quarterly would put a portion of it over that line: formally reviewed, permanently identified, properly indexed, and citable as scholarship rather than as a government web page. It would also give the unit a publishing rhythm and a standing invitation to outside authors, which the Hub's continuous model never creates on its own.

The costs stay real and are set out below: a second system to run, keep updated, back up, and staff — and, harder than any of that, an editorial board and reviewers willing to do the work.

Could the Studio be built out to do what OJS does?

Much of it — but not the parts that matter most

Closer than it looks. The Studio already has user accounts and roles, a draft-to-published sequence, a required approval step, lists of authors and topics it keeps track of, drafts and previews, and attached files. The new Studio adds the ability to highlight a passage and leave a comment on it. From that base, inviting several reviewers, running rounds with deadlines, sending reminders, and hiding names so reviewers and authors don't see each other are additions to something that already exists, not a new product from scratch.

Two things don't yield to that:

  • Issuing DOIs is a commitment, not a feature. The programming needed to send one to Crossref is small. What isn't small is the rest: the membership, the annual fee, the identifier registered in ICJIA's name, and the permanent promise to keep every DOI working. Those are the same whichever tool sends the request — and OJS has that path built and proven already.
  • Getting listed by Google Scholar, DOAJ, and library catalogues means describing every article in the precise formats each service expects, and keeping up as those change. It can be built, but it is fiddly, unglamorous, never quite finished — and those services already recognize OJS on sight.

And the counterweight: anything built into the Studio, ICJIA maintains forever. The review machinery inside OJS is maintained by the nonprofit that makes it, at no cost to us. Building our own trades a hosting burden for a development burden. Neither is free.

What the draft Hub 2.0/Studio 2.0 “Copperhead” rebuild fixes

Hub 2.0 is the other proposal on the table, and it is worth seeing plainly, because it answers several of the current setup's weaknesses without any of the costs above.

  • It gets off unsupported software. The program storing the Hub's content stopped receiving security updates in 2022, and the Hub currently sits tangled inside the main website's code. The rebuild moves it onto current, supported software and stands it on its own. The Studio is likewise rebuilt off tools no longer being maintained.
  • Reviewer comments finally go on the record. The new Studio lets a reviewer highlight a passage and leave a comment on it, kept with the draft. That is exactly what today's single approval step lacks — and, as above, what any fuller review process would be built on.
  • The web addresses don't change. Keeping every existing address working is a firm requirement, checked automatically before launch. The whole search-standing problem never arises.
  • Readers can search inside documents. Not just titles and summaries but the words inside published PDF reports, opening a long report at the first match.
  • Accessibility is checked on every single change, automatically, against the standards the agency is required to meet — plus a full manual walkthrough already completed. Today that checking happens only now and then, by hand.
  • It has been tested, and attacked on purpose. 946 automatic checks run over it whenever anything changes, and four separate security reviews had testers actively trying to break in. Nothing critical was found.
  • There is far less to break into. The public site is built ahead of time and handed out as fixed files, with no live database or passwords sitting behind it — quicker for readers and much harder to attack.

It is built and working, waiting on a decision — the same position as this OJS test. The two are not rivals. One modernizes how ICJIA publishes what it already publishes; the other asks whether the agency wants to publish something it doesn't yet.

The question for R&A isn't which tool. It's whether ICJIA wants to publish a peer-reviewed journal — a quarterly of the agency's own research, reviewed and citable, on top of the Hub rather than instead of it. If that is worth having, OJS alongside the Hub is the cheapest correct way to get it, and this test server is the sensible way to find out. If what's actually wanted is more rigor on Hub content, that belongs in the Studio, not in a second system. Either way the software is the easy part: the editorial board, the reviewers willing to work for free, and the steady stream of submissions are what a test server can't tell us we have.

What a DOI is, and why we're careful with them

10.12345/icjia.2026.001

A DOI, or Digital Object Identifier, is a permanent ID for a published article. The first part identifies the publisher; the second identifies the article. Anyone, anywhere, can type it into doi.org and land on the article, no matter where the article lives.

The problem it solves

Web addresses break. Sites get redesigned, moved, or shut down, and every citation pointing at the old link dies.

A DOI separates what an article is from where it currently sits. Move the article, update one record, and every citation ever written still works.

Why research depends on it

Google Scholar, citation counts, reference managers, and library catalogs all key on the DOI. Many journals require DOIs in reference lists. Funders and indexes treat DOI assignment as the mark of a real journal.

For ICJIA it's how our research gets found, cited, and counted.

Why it can't be undone

Issuing a DOI is a promise to keep it working forever. It's registered with a nonprofit called Crossref under the publisher's name. You can update where it points; you can never delete it.

A DOI issued from a test server would point at a machine we plan to erase, with ICJIA's name attached.

How OJS handles DOIs

  1. ICJIA joins Crossref (the nonprofit that runs the DOI registry) and receives a publisher prefix. At ICJIA's size, membership is a few hundred dollars a year.
  2. An editor turns on DOIs in the journal settings and picks a naming pattern.
  3. OJS generates a DOI for each article automatically. At this point it exists only inside our system.
  4. OJS sends the article's details to Crossref, and the DOI becomes real and permanent. This step will not be turned on during the test.
  5. The DOI appears on the article page. If the site ever moves, one update to Crossref redirects every citation to the new address.

Steps 1 through 3 are safe to explore. Step 4 requires a Crossref account and credentials that the test server simply won't have, so nothing can be registered by accident. For the same reason, the test won't be submitted to Google Scholar, DOAJ, or any other index.

What can carry a DOI

More than one might expect. OJS treats each article as its own citable object, and a setting decides how far down that goes:

  • Each article. The standard practice, and the one that matters. Every paper gets its own permanent link, so it can be cited directly rather than through the issue it sat in.
  • A single file inside an article. A dataset, or the PDF as distinct from the web version, can carry its own DOI — meaning a dataset can be separately citable, not merely an attachment.
  • A whole issue. One identifier for a volume or number as a unit.
  • The journal itself. A single identifier standing for the periodical overall.

The prefix is the part Crossref assigns and it always identifies ICJIA. The suffix names the item, and OJS can build it automatically from a pattern — giving something like icjia.vol1issue2.article5 — or an editor can type one in by hand for a particular article.

Why this test setup is low risk

No licence to buy

OJS is open source. The test server costs a few dollars a month and can be switched off any time. Production is not free — see what it would actually cost, below.

Nothing to lose

The test lives at a temporary address (ojs.icjia.cloud) with made-up content. Nothing is published, indexed, or permanent.

Well-trodden ground

OJS has been in development since 2001 and runs on ordinary web hosting, the same kind IDS already manages for ICJIA's other sites.

Same hands

The test is being built by IDS, which already runs 15+ ICJIA web properties. This is a smaller job than most of them.

Who runs it, day to day

Once OJS is installed, running the journal is a browser job: creating it, adding people, moving submissions through review, building issues, publishing. None of it needs server access, and the administrator will not be given any.

That work has its own guide so this page can stay about the decision: Running the journal — a guide for the OJS administrator. It covers first login, creating the journal, the roles, adding people, naming a backup administrator, and the one end-to-end test that answers whether OJS fits how R&A works. It also draws the line between what the administrator fixes and what needs a ticket.

Two things IDS asks of R&A. Name a backup administrator early — one admin with a forgotten password is the most common OJS problem there is, and R&A owns that succession. And if the answer turns out to be no, say so the same day: the server bills every month it exists and there is nothing on it worth keeping. A one-line email is enough; no approvals, no paperwork.

If we decide to adopt it

Five things would need to happen before OJS could host a real journal. None are blockers, and each has a clear owner.

A bigger server

The test machine is deliberately tiny. A real journal needs more room. On-premise is preferred, run by someone in R&A or IDS with remote access. AWS is a workable alternative; Karl, a former R&A center manager, has run one there.

What it would actually cost. The software stays free, but a real journal is not a $0 line item. Budget for a production server sized for the load, a Crossref membership if DOIs are wanted (a few hundred dollars a year at ICJIA's size), the Laravel Forge subscription if the server is managed that way, and IDS time for upgrades and backup testing. None of these is large, and none is a surprise — but “free software” and “free to run” are different claims, and only the first one is true.
