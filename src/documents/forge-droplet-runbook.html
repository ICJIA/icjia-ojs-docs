How do I install OJS and OPS?

Runbook for a brand-new Laravel Forge server on DigitalOcean, carrying two separate installations on one box: the CPU-eating package to remove first, the reason the site didn't serve, the prep before installing OJS, the install itself, the Mailgun hookup, then OPS as a second site — and the hardening, memory tuning, backups, upgrades and restores that from then on have to cover both.

Read this first: why the early steps exist

Linux only. These commands are for Ubuntu, not Windows. Everything on this page was run and verified on Ubuntu 26.04, the version in the header above, and the commands assume that. None of it transfers to Windows. Windows Server is a completely separate test environment — different web server, different PHP packaging, different file permissions, different failure modes — and nothing below can be translated line by line. If OJS is going to be installed on Windows, that needs its own set of docs, written against an actual Windows install by whoever does it.

Worked through 3–6 September 2026 on the OJS/OPS proof-of-concept droplet. The hostname and paths below are specific to that box; everything else is general to Forge on DigitalOcean.

Two applications end up on this box, and they are two separate installations. OJS and OPS are the same codebase geared for different jobs, but they do not share an install: separate web addresses, separate nginx sites, separate databases (their table names collide), separate files directories and separate user tables. Read the runbook front to back for the first one; the “Installing OPS as the second site” section after the mail setup (steps P1–P8) is the delta for the other. From that point on, everything operational — memory, backups, upgrades, restores — is a two-application job, and the sections below say so where it matters.

This runbook opens with fixes, not installation, because a freshly provisioned Forge droplet on DigitalOcean did not work as delivered. Out of the box it showed excessive CPU usage on an idle machine and nginx would not start, so the site was unreachable before a single line of OJS had been unpacked. Steps 0 through B document what had to be done to the Forge server before any real work could begin.

Several of those steps are specific to how Forge provisions a box (nginx from the nginx.org mainline repo, a hand-compiled Brotli module, a Laravel-tuned PHP-FPM) and will not apply to a vanilla Ubuntu install that uses the distro's nginx package. The MTA-STS CPU bug is stock Ubuntu and applies anywhere. The translation table below says which is which. If you're on plain Ubuntu, skim the fixes for the symptoms and skip straight to the pre-install prep.

What this page publishes, on purpose, and what it never will. It publishes the hostnames, paths, login user and configuration of a disposable test box, because a runbook without them cannot be followed. It never publishes a password, key, token or other credential — a build test refuses the whole site if one appears — and nothing on it is a production value. A production build gets its own settings, which stay off this site.

The plan, in order

Every step on this page, in the order to do them on a fresh box. The letters are the step labels in the sections that follow. On a plain Ubuntu server rather than a Forge droplet, skip 0–B unless the symptoms are there, and use the translation table for where things live.

  1. S1–S3 · Get on the box. Send IDS an Ed25519 public key, wait for it to be added by hand, connect as forge.
  2. 0 · Quiet the CPU. Purge postfix-mta-sts-resolver if mta-sts-daemon is burning a core. Stock Ubuntu bug; applies anywhere.
  3. 1–3 · Diagnose the dead site. DNS, then nginx -t, then the firewall — in that order, stopping at the first failure.
  4. A–B · Fix nginx and pin it. Comment out the Brotli module Forge compiled against an older nginx, start nginx, apt-mark hold nginx. Forge-specific.
  5. C–H · Prepare for a PHP app, before the tarball. Settle the hostname; find the web root; install PHP 8.3 (OJS 3.5 does not run on 8.5); raise the upload cap in nginx; rewrite the PHP location with path-info, the 8.3 socket, the 600 s timeouts and the denies; create a utf8mb4 database; prove it all with the readiness page.
  6. I–K · Install OJS. Download the tarball on a workstation and scp it up; unpack into the web root with uploads outside it; run the web installer; lock down config.inc.php and set the day-one options.
  7. L–N · Outgoing mail. Verify the Mailgun domain with DKIM, add an SMTP credential, write the [email] block with the envelope-sender and DMARC settings, test with a password reset.
  8. P1–P8 · OPS as the second site. Same box, same MySQL, everything server-level inherited from the OJS build. Per site: DNS and the Forge site, step F's block copied into the new site file, a separate database, the tarball and a files directory, the installer, the [email] block and a mail test, then the backup line and the memory tuning two applications need on 2 GB.
  9. Backups, then handoff. Install pkp-backup, run it once and count six files, then hand over two admin logins and point at the two administrator guides.
  10. Later: U1–U5 upgrades, R1–R3 restores. Both applications, one at a time, from the command line; rehearse a restore quarterly.

Laravel Forge, in one paragraph

Laravel Forge is a paid dashboard from the Laravel team that provisions an Ubuntu VM on DigitalOcean, AWS, Linode or similar with a standard stack — nginx, PHP-FPM, MySQL or Postgres, Redis, ufw, fail2ban and a forge user with sudo — and then makes adding a site, issuing a Let's Encrypt cert, switching PHP versions or creating a database a button instead of a config edit. It has nothing to do with the Laravel framework beyond who makes it, it is fine for any PHP app, and nothing it does is hidden: the result is a plain Ubuntu server you SSH into and treat like any other, and it writes the same files you would.

If you're on plain Ubuntu instead

Almost everything in this runbook is Ubuntu, nginx, PHP, and MySQL. Forge only changes where a few things live and which button does the edit. Translate as follows:

What's Forge-specific here: the Brotli breakage in step A, and the Laravel-tuned defaults that steps D–F replace. Forge installs nginx from nginx.org's mainline repo and hand-compiles the Brotli module, which is why an apt upgrade orphaned it; Ubuntu's own nginx package with libnginx-mod-brotli (or no Brotli at all) doesn't have that problem. The MTA-STS CPU bug in step 0 is stock Ubuntu behavior and applies to any install, and the PHP-version, path-info and timeout requirements apply to any host, whatever its defaults happen to be.

Getting on the box: SSH access

You only need SSH if you need the server itself — the operating system, nginx, PHP, MySQL, or the files on disk. Everything about running the journal or the preprint server is done in the OJS or OPS browser admin: users and roles, sections, the review workflow, email templates, appearance, plugins. If the thing you are trying to change has a settings screen, it does not need a shell, and opening one is the wrong move.

In practice the shell is for the work in this runbook and little else: installing or upgrading OJS and OPS, changing PHP or nginx limits, editing config.inc.php, reading server logs, and restoring from backup. Managers and the application administrators are not given shell access and do not need it — the handoff section near the end of this page is the whole job in a browser.

There is no password login. The server accepts OpenSSH public keys only, and a key has to be added to the box by hand — there is no self-service enrollment, and Forge will not do it for you on a server that already exists. Contact IDS to request access, and send the public half of your key.

Access is granted on a need-to-access basis only. A ticket asking for the shell should say what you need to do on the server that cannot be done in the browser. If the task turns out to be a settings screen, IDS will point you at it rather than issue a key — fewer keys on the box is the point, not an obstacle.

S1

Send IDS a public key

Ed25519, passphrase-protected. Send the .pub half and nothing else; if a private key is ever exposed, say so and rotate rather than hoping.

bash
ssh-keygen -t ed25519 -C "yourname@icjia" -f ~/.ssh/id_ed25519_ojs
cat ~/.ssh/id_ed25519_ojs.pub
S2

Wait for it to be installed

Raise a Freshservice ticket and paste the public key into it. IDS appends it to authorized_keys for the forge user by hand; there is no enrollment endpoint and Forge will not do it on an existing server. Until someone does that, the key does nothing and your connection is refused.

S3

Connect

The login user is forge, not root; it owns the web root everything below refers to.

bash
ssh -i ~/.ssh/id_ed25519_ojs forge@ojs.icjia.cloud

Permission denied (publickey) here almost always means the key is not on the box yet rather than anything wrong with your client — check with IDS before debugging locally. When someone leaves the project, tell IDS so their key can be removed. Keys outlive involvement unless somebody takes them out.

What was actually wrong

Symptom 1

Site unreachable

curl ojs.icjia.cloud → Failed to connect… port 80. Not a 404 or 502 — nothing listening at all. DNS was correct; ufw allowed 80/443; the nginx site file looked normal.

↓

Cause: version-mismatched Brotli module

Forge installs nginx from nginx.org's mainline repo, then compiles the Brotli module from source against that exact build (1.31.4). An apt upgrade later bumped nginx to 1.31.5. Nginx refuses a module built for another version, the load_module line fails, the whole config fails, and nginx never starts. Apt can't fix it — it doesn't know the module exists.

Symptom 2

40% CPU on an idle box

top showed mta-sts-daemon at 30–40% of a core within minutes of every boot, load average near 2 on a 2-vCPU machine.

↓

Cause: known Ubuntu bug

postfix-mta-sts-resolver arrived with the mail stack. Its default sqlite cache backend spins in a tight timeout loop (python-aiosqlite). Open bug since 2023. Fix is either the cache: type: internal setting or, if you don't run local Postfix, remove it.

First: quiet the CPU

Do this before anything else. A fresh 2-vCPU droplet should sit near idle; ours was at 40% busy with a load average near 2, which makes every later step slower and muddies any diagnosis. The culprit is a package Forge's mail stack pulls in, and it's a known Ubuntu bug, not something you misconfigured.

0

Confirm it's mta-sts-daemon, then remove it

bash
top -bn1 | head -12                        # look for mta-sts-daemon near the top, with low TIME+ but high %CPU

postfix-mta-sts-resolver exists only to hand MTA-STS policies to a local Postfix sending mail. Its default sqlite cache backend spins in a tight timeout loop in python-aiosqlite (Ubuntu bug open since 2023). OJS sends through Mailgun over SMTP, so local Postfix isn't in the picture and the daemon is dead weight.

bash
sudo apt purge postfix-mta-sts-resolver
sudo apt autoremove                        # drops the orphaned python3-aio* libs it pulled in
top -bn1 | head -5                         # idle should climb past 95% within a minute
Two traps: systemctl stop postfix and systemctl stop mta-sts-daemon both fail with "unit not loaded" — the real unit is postfix-mta-sts-resolver. And the _mta-sts group warning on purge is harmless.

If you ever do need it (a real local Postfix relaying outbound mail), keep the package and set cache: type: internal in /etc/mta-sts-daemon.yml, then sudo systemctl restart postfix-mta-sts-resolver.

Diagnosis, in the order that worked

Each check rules out one layer. Stop when one fails.

1

Is DNS pointing here?

bash
dig +short ojs.icjia.cloud
curl -4 -s ifconfig.me; echo
ip -4 addr show eth0 | grep inet
Gotcha: plain curl ifconfig.me answers over IPv6 on a DO droplet, so it won't match the A record. Force -4.
2

Is nginx listening, and does its config parse?

bash
sudo ss -tlnp | grep -E ':80|:443'
sudo nginx -t
sudo systemctl status nginx --no-pager | head -5
What we saw: ss printed nothing, and nginx -t said module "…ngx_http_brotli_filter_module.so" version 1031004 instead of 1031005. That one line was the whole outage.

Decoding the numbers: nginx encodes its version as NGINX_VERSION = major×1,000,000 + minor×1,000 + patch, so 1031004 is 1.31.4 and 1031005 is 1.31.5. Dynamic modules built with --with-compat still embed the exact version they were compiled against, and nginx hard-fails on any mismatch rather than degrading. sudo journalctl -u nginx -n 30 --no-pager shows the same error from the failed start, if you'd rather read it there.

3

Firewall (only if 1 and 2 pass)

bash
sudo ufw status

Forge opens 22/80/443 in ufw. If those are allowed and nginx is listening but the site still refuses, the block is a DigitalOcean cloud firewall attached in the control panel (Networking → Firewalls) — it sits in front of ufw.

The fixes

A

Disable the broken Brotli module, start nginx, pin the version

Brotli is optional compression; gzip still works. Rebuilding the module against the new nginx is possible but breaks again on the next upgrade.

bash
grep -n brotli /etc/nginx/nginx.conf          # expect two load_module lines; the sed below matches them, not their numbers
sudo sed -i '/^[[:space:]]*load_module.*brotli/s|^|# |' /etc/nginx/nginx.conf
sudo nginx -t
sudo systemctl start nginx
sudo systemctl enable nginx
sudo apt-mark hold nginx                       # stop apt from drifting nginx under Forge's compiled bits
curl -I http://ojs.icjia.cloud                   # 200, or a 301 to https once Forge has issued the cert
If nginx -t still complains about an unknown brotli directive: grep -rn brotli /etc/nginx/ and comment those lines too.

Alternative: rebuild the module against the installed nginx

If you actually want Brotli (it's ~15–20% smaller than gzip on text, which matters little for a journal site), rebuild the dynamic module from the same source Forge used. Needs libbrotli-dev (already present) and build tools.

bash
nginx -v                                        # e.g. nginx/1.31.5 — the version to build against
nginx -V 2>&1 | grep -o 'configure arguments:.*'  # keep for reference; --with-compat is what matters
sudo apt install -y build-essential libpcre2-dev zlib1g-dev libssl-dev git
cd /usr/local/src
sudo git clone --recurse-submodules https://github.com/google/ngx_brotli.git
sudo curl -LO https://nginx.org/download/nginx-1.31.5.tar.gz && sudo tar xzf nginx-1.31.5.tar.gz
cd nginx-1.31.5
sudo ./configure --with-compat --add-dynamic-module=../ngx_brotli
sudo make modules
sudo cp objs/ngx_http_brotli_*_module.so /etc/nginx/modules/
sudo sed -i '/^# *load_module.*brotli/s|^# ||' /etc/nginx/nginx.conf   # un-comment the two load_module lines
sudo nginx -t && sudo systemctl reload nginx

The catch is durability: this .so is again tied to 1.31.5, so the next nginx package upgrade re-breaks it unless nginx stays on hold. Forge's own approach on a fresh provision is exactly this build, which is why the hold matters either way.

B

Confirm the hold, and know what's still going to move

bash
apt-mark showhold                              # should list nginx
apt list --upgradable 2>/dev/null            # what unattended-upgrades or the next apt upgrade will touch
grep -n Unattended-Upgrade /etc/apt/apt.conf.d/50unattended-upgrades | head

Unattended-upgrades on Ubuntu pulls from the -security pocket by default and leaves third-party repos (nginx.org, sury.org, redis.io) alone unless they're added to Allowed-Origins. So the original drift almost certainly came from Forge's post-provision apt upgrade, not from nightly patching. The hold protects against both. If you ever need to move nginx deliberately: sudo apt-mark unhold nginx, upgrade, then rebuild or re-comment Brotli, then re-hold.

The CPU fix from step 0 is the other prerequisite; if it was skipped, every PHP-FPM worker below is competing with a busy loop for two cores.

Pre-install prep for a PHP app

Forge's defaults are tuned for Laravel, not for a document-heavy app. All of these bit us.

Settle the hostname first. This box was first provisioned as ojs.icjia.app and renamed to ojs.icjia.cloud before installing OJS, because Mailgun was already verified on icjia.cloud. Pre-install is the right time: OJS bakes the hostname into config.inc.php and the database, but until it's installed the name lives only in DNS, the Forge site record, and its nginx config. The swap is: add the A record, rename (or delete and recreate) the site in Forge, issue a new Let's Encrypt cert, curl -I the new name, and redo the nginx edits of steps E and F on the fresh site file. Everything server-level in steps 0–B survives the rename.

C

Know where the web root is

bash
sudo head -20 /etc/nginx/sites-available/ojs.icjia.cloud   # look for the root line

This site's root was /home/forge/ojs.icjia.cloud — no public/ subfolder — because the Forge site's web directory was set to /. Forge no longer writes a placeholder page, so the directory contains only an empty index.php.

D

Match PHP to what OJS supports — before you run the installer

Do this before unpacking the tarball. Forge provisions the newest PHP its Ubuntu release offers, which is routinely newer than the PHP any OJS release was tested against, and the installer fails in a way that does not name the cause. On this box it was Fatal error: Smarty Compiler: Syntax error in template "app:installinstall.tpl" … unknown tag 'translate'. That tag is registered in PKPTemplateManager::initialize(); seeing it unregistered means initialization aborted earlier, and the real fault above it in the log was Locale::setDefault(): null given — a PHP 8.5 incompatibility in the vendored components, 8.5 being newer than anything OJS 3.5.0-5 was tested on. Fix: run the site on PHP 8.3: inside 3.5's support window, security-supported through end of 2027. Not 8.1 — it's EOL.

Forge only offered 8.5 for this Ubuntu release, but the sury PPA it provisioned from carries 8.3, so install it manually, mirroring the 8.5 extension set Forge chose:

bash
apt-cache policy php8.3-fpm | head -3
sudo apt install -y $(dpkg -l | awk '/^ii  php8\.5/ {print $2}' | sed 's/8\.5/8.3/')
# Forge's pool runs FPM as forge, stock pool runs as www-data; copy Forge's:
sudo cp /etc/php/8.5/fpm/pool.d/www.conf /etc/php/8.3/fpm/pool.d/www.conf
sudo sed -i 's/php8\.5-fpm\.sock/php8.3-fpm.sock/' /etc/php/8.3/fpm/pool.d/www.conf
sudo sed -i 's/^upload_max_filesize = .*/upload_max_filesize = 64M/; s/^post_max_size = .*/post_max_size = 64M/; s/^max_execution_time = .*/max_execution_time = 300/' /etc/php/8.3/fpm/php.ini
sudo systemctl enable --now php8.3-fpm && sudo systemctl restart php8.3-fpm
ls -l /var/run/php/php8.3-fpm.sock

Then change fastcgi_pass in the site's PHP location to unix:/var/run/php/php8.3-fpm.sock, sudo nginx -t && sudo systemctl reload nginx, clear cache/t_compile/* and cache/t_cache/*, reload the installer.

Forge doesn't know 8.3 exists. Its site settings will still say 8.5, and if anyone changes the site's PHP version in the Forge UI it will rewrite fastcgi_pass back to the 8.5 socket. Fine on dev; worth a comment in the nginx file so the next person understands why the socket doesn't match the dashboard.
E

Raise the upload cap in nginx, and check the pool

Step D already set upload_max_filesize, post_max_size and max_execution_time in the 8.3 php.ini. Forge's defaults were 2M, 8M and 30, and editing them through Forge's UI did not land in php.ini; editing the file directly did. Confirm, then check the pool, because a php_admin_value there beats php.ini:

bash
grep -n '^upload_max_filesize\|^post_max_size\|^max_execution_time' /etc/php/8.3/fpm/php.ini
grep -rn 'upload_max_filesize\|post_max_size' /etc/php/8.3/fpm/pool.d/     # expect nothing

Nginx has its own cap, default 1M, and it rejects the request with a 413 before PHP ever sees it. Add to the site config, inside the server block (Forge's site nginx editor works fine):

nginx — per site, inside server { }
client_max_body_size 64M;

Or set it once for every site on the box by putting the same line inside the http { } block of /etc/nginx/nginx.conf; a server block can still override it. Scope rule: the directive is valid in http, server, and location, and the most specific one wins. Keep it equal to or larger than PHP's post_max_size, which in turn must be ≥ upload_max_filesize.

bash — global variant
sudo sed -i '/^http {/a \    client_max_body_size 64M;' /etc/nginx/nginx.conf
grep -n client_max_body_size /etc/nginx/nginx.conf
bash
sudo nginx -t && sudo systemctl reload nginx
F

Rewrite the site's PHP location before the installer ever runs

Forge's site file is tuned for Laravel: its location ~ \.php$ only matches URIs that end in .php, its FastCGI read timeout is 60 s, and its fastcgi_pass still points at the 8.5 socket. OJS routes look like /index.php/journal/article/view/12 — including the installer's own /index.php/index/en/install, which on this box redirected in a loop (ERR_TOO_MANY_REDIRECTS) until this block was in — and the install itself runs well past 60 s on a 2 GB box, so nginx drops the connection while PHP-FPM keeps going. Fix all of it now, in one edit, and the installer is boring. Replace Forge's block with this; the only differences from Forge's are the first line, the socket, the two trailing fastcgi_params and the timeout:

nginx — replaces the location ~ \.php$ block
location ~ \.php(/|$) {
    fastcgi_split_path_info ^(.+\.php)(/.+)$;
    fastcgi_pass unix:/var/run/php/php8.3-fpm.sock;   # 8.3, not the 8.5 Forge still shows in its UI
    fastcgi_index index.php;
    include fastcgi_params;
    include forge_fastcgi_defaults;
    fastcgi_param PATH_INFO $fastcgi_path_info;
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    fastcgi_read_timeout 600;
}

Nginx hardening for OJS, in the same edit. Because nginx ignores .htaccess, the protections OJS ships in those files don't apply. Forge's default location ~ /\.(?!well-known).* already blocks dotfiles. Add explicit denies for the config and the cache, inside the server block above the PHP location:

nginx
location ~ ^/(config\.inc\.php|config\.TEMPLATE\.inc\.php)$ { deny all; }
location ~ ^/(cache|lib/pkp/lib/vendor)/.*\.php$ { deny all; }
bash
sudo nginx -t && sudo systemctl reload nginx

Then the PHP-FPM half of the timeout. Raising nginx's alone moves the failure one layer down: a 502 with recv() failed (104: Connection reset by peer), which is PHP-FPM's request_terminate_timeout killing the worker (Forge sets it to 60 in the pool, and step D copied that into 8.3's); /var/log/php8.3-fpm.log says execution timed out … terminated on signal 15. Raise it now:

bash
sudo sed -i 's/^request_terminate_timeout = .*/request_terminate_timeout = 600/' /etc/php/8.3/fpm/pool.d/www.conf
sudo php-fpm8.3 -t && sudo systemctl restart php8.3-fpm

Stack: nginx fastcgi_read_timeout 600 ≥ FPM request_terminate_timeout 600 ≥ PHP max_execution_time 300. With the uploads directory outside the web root (step I), galley PDFs and reviewer files can only be fetched through OJS's access checks, never by URL; the denies above do the same for the config and the caches.

G

Create the app database (Forge only makes forge)

bash
mysql -u forge -p -e 'SHOW DATABASES;'
mysql -u forge -p -e 'CREATE DATABASE ojs CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;'

utf8mb4, not utf8 — MySQL's utf8 is 3-byte and chokes on emoji and some CJK. If forge lacks CREATE rights, use Forge → server → Database → Add Database, which runs as root and grants access.

The readiness check

H

Prove the stack before unpacking anything

A throwaway index.php that prints what the installer will test. Fill in $db, load it once, then delete it and reset the DB password — it reveals paths and, with credentials in, is a web-readable secret. No closing ?> on purpose (trailing whitespace after it would break the header() call).

php — index.php
<?php
// Temporary server check — delete before installing the app.
header('Content-Type: text/plain');

echo "ojs.icjia.cloud is up\n";
echo "Time:    " . date('c') . "\n";
echo "Server:  " . php_uname('n') . "\n";
echo "PHP:     " . PHP_VERSION . " (" . php_sapi_name() . ")\n";
echo "ini:     " . php_ini_loaded_file() . "\n";
echo "Root:    " . __DIR__ . "\n";
echo "HTTPS:   " . (!empty($_SERVER['HTTPS']) ? 'yes' : 'no') . "\n\n";

bash
curl -s https://ojs.icjia.cloud          # everything should read ok / 64M / 300 / connected
rm ~/ojs.icjia.cloud/index.php           # then reset the DB password in Forge
Error 1049 "Unknown database" means PHP reached MySQL and authenticated; the database just doesn't exist yet. Go back to step G.

Install OJS

OJS is a plain PHP application: nginx serves static assets and hands .php to PHP-FPM over the socket already in the site config. No daemon, no port, no proxy. The tarball ships with Composer dependencies vendored, so there's no build step.

I

Unpack into the web root

Post-install: outgoing mail via Mailgun

The OJS installer never asks about email. Mail is configured after install by editing config.inc.php in the OJS root. No restart needed; PHP reads the file on each request. There is no UI for these settings.

Done on this box. Outgoing mail is configured and sending as of 4 September 2026. The steps below are what to repeat on the next server; the values in them are the ones this one uses.

Why Mailgun. Only because ICJIA already uses it for every other web-related mail task, so the sending domain, its DNS records and an account existed before OJS did, and with this install it is verified end to end for both applications. Nothing in OJS or OPS depends on it: they want an SMTP host, a port, a credential and a sending domain whose SPF and DKIM records are in place, and any transactional provider supplies those the same way — Amazon SES, SendGrid, Postmark, Mailjet, Brevo, SparkPost, among others. The provider for a production build is whoever builds it to choose, subject to DoIT approving it for an illinois.gov address. Substitute its SMTP host, port and credential in the [email] block below and keep everything else.

L

Set up the sending domain in Mailgun first

On this project the root domain icjia.cloud was already set up in Mailgun (MX → mxa/mxb.mailgun.org, SPF at @). Before relying on it, open Sending → Domains in Mailgun and confirm it shows verified with a green check on the DKIM record (a TXT at <selector>._domainkey.icjia.cloud); SPF alone gets mail sent but not trusted. Then on the domain's SMTP Credentials tab, Add new SMTP user and create a dedicated login for OJS (ojs@icjia.cloud). Don't reset postmaster@: another mailer uses it. The password is shown once; it is not the API key. The envelope sender stays admin@icjia.cloud because that address already has an inbound Route; the SMTP login and the envelope sender are independent, and any address on the verified domain works for either.

Inbound consequence: with MX at the root pointing to Mailgun, replies to ojs@icjia.cloud land in Mailgun's receiving side and vanish unless a Route (Receiving → Routes) forwards them to a real mailbox. Fine for one-way system mail; add the Route if editors should be able to reply.
Free/sandbox tier only delivers to addresses you pre-authorize. A verified custom domain (paid plan) is needed for real testing with colleagues.

Port 587 pairs with tls; port 465 pairs with ssl. Mailgun accepts both. force_default_envelope_sender = On keeps the envelope sender on the verified domain even when OJS sends "on behalf of" an editor with an unrelated address, which is what keeps SPF aligned. force_dmarc_compliant_from = On does the same for the visible From header: without it, a review invitation goes out "From: editor@illinois.gov" via Mailgun, fails illinois.gov's DMARC, and gets junked or rejected, including by DoIT's own gateway. With it, From is admin@icjia.cloud and the editor lands in Reply-To. Both settings are gated behind allow_envelope_sender = On.

Protect the file: it now holds DB and SMTP passwords. chmod 640 it and confirm the explicit nginx deny from step F is in place (curl -sI https://ojs.icjia.cloud/config.inc.php → 403). Nginx never executes .htaccess, so OJS's shipped Apache rules are inert here.
N

Test it

Fastest end-to-end check: go to https://ojs.icjia.cloud/index.php/index/login/lostPassword, request a reset for the admin account, then open Mailgun → Sending → Logs. You'll see the message accepted or the exact SMTP rejection. Common rejections: unverified domain (DNS records not live yet), wrong credential (used the API key or account email), or a from address on a domain Mailgun doesn't own.

When a user reports "I'm not getting email": run the same lost-password test as admin first. Then, in order: (1) wait — delivery to state mailboxes can take up to 15 minutes; (2) check spam/junk — DoIT tags all outside mail [EXTERNAL] and OJS mail is outside; (3) check Mailgun's logs for the recipient address — Mailgun retains only 5 days, so old reports can't be verified; (4) if Mailgun shows delivered and it still never arrived, DoIT's mail gateway held or dropped it, and that's a DoIT ticket, not an OJS problem. Mailgun "delivered" means handed to DoIT's servers, not that a mailbox received it.

If nothing reaches Mailgun at all, tail OJS's log while you retry:

bash
sudo tail -f /var/log/nginx/*-error.log        # PHP errors land here under Forge's site config

P2

The nginx site block, before the tarball

Forge writes the new site file with the same Laravel defaults that broke the OJS installer (errors 6, 8 and 9 in the table below), so fix it now rather than rediscovering them. Open /etc/nginx/sites-available/ops.icjia.cloud and, inside server { }: add client_max_body_size 64M; from step E, add the two deny locations from step F, and replace Forge's location ~ \.php$ block with step F's \.php(/|$) block — the 8.3 socket, PATH_INFO and SCRIPT_FILENAME, fastcgi_read_timeout 600. Nothing in those blocks is site-specific, so copy them verbatim from the OJS site file; leave Forge's own server_name, root, ssl_certificate, error_log and include forge-conf/… lines alone, because they already carry the new site's paths. Add the same one-line comment at the top saying the socket is 8.3 on purpose and the Forge PHP setting must not be touched.

bash
sudo nano /etc/nginx/sites-available/ops.icjia.cloud
sudo nginx -t && sudo systemctl reload nginx
grep -n 'fastcgi_pass\|fastcgi_read_timeout\|client_max_body_size\|deny all' /etc/nginx/sites-available/ops.icjia.cloud

PHP and PHP-FPM need nothing: the 8.3 pool, its php.ini limits and its request_terminate_timeout are server-wide, and the new site inherits all of them through fastcgi_pass. The grep should show the 8.3 socket, 600, 64M and two denies.

Memory with two apps on 2 GB

After the second install: 952 MB used, 267 MB in swap at idle. MySQL was resident at ~525 MB with innodb_buffer_pool_size already at the 128 MB default; the bulk was performance_schema. Two changes brought it to 870 MB used, 31 MB swap, 1.1 GB available:

bash
sudo tee /etc/mysql/mysql.conf.d/zz-lowmem.cnf > /dev/null << 'EOF'
[mysqld]
performance_schema = OFF
EOF
sudo systemctl restart mysql                    # mysqld 525 MB → ~300 MB RES

sudo systemctl disable --now php8.5-fpm         # nothing points at the 8.5 socket; frees its master + idle workers
free -m
top -bo %MEM | head -14
One consequence of disabling 8.5: Forge still believes both sites run on 8.5, and a PHP-version change in its UI rewrites fastcgi_pass to the 8.5 socket — now a socket with nothing behind it, so the site goes 502 until the step F block is put back. Leave the Forge PHP setting alone, and say so in a comment at the top of each site file.

Don't lower innodb_buffer_pool_size below the default; 128 MB is already the floor for two small InnoDB databases. If swap creeps up again, journalctl --vacuum-size=100M and SystemMaxUse=100M in /etc/systemd/journald.conf is the next lever. Beyond that, it's a bigger droplet, which is the production conversation anyway.

The pattern behind 6–9

Forge tunes for Laravel: short requests, no path-info routing, aggressive timeouts. OJS is the opposite on all three counts — long installer and upgrade requests, /index.php/journal/… URLs, and a 2 GB box that makes everything slower. Every one of those four errors is the Laravel default meeting an OJS assumption. A production host provisioned any other way (DoIT's Ubuntu image, AWS, on-prem) will have different defaults, but the same four questions need answering before the installer runs:

QuestionWhere to lookNeeds to be
Does the PHP location match /index.php/anything?nginx site config, location ~ \.php…\.php(/|$) with PATH_INFO passed
How long will nginx wait for PHP?fastcgi_read_timeout≥ 600 s
How long will FPM let a worker run?request_terminate_timeout in the pool≥ 600 s, or 0
How long will PHP let a script run?max_execution_time in php.ini≥ 300 s for install/upgrade

Plus the two that aren't timeouts: PHP version inside OJS's stated support range (not the newest available), and upload limits in both php.ini and nginx. Check all six on the prod box before unpacking a tarball, and the install is boring, which is the goal.

Backups on the dev box

What's on now: DigitalOcean's built-in droplet backups, on the weekly schedule, not daily. That's deliberate for a dev box: a full-image snapshot once a week is enough to recover from a wrecked server, and daily would double the (small) backup line item for content that's all fake. It's a whole-disk image, restored from the DO control panel (droplet → Backups → Restore), and it's the only backup in place at the moment.

The script below adds a nightly, application-level layer on top of that: a database dump plus the files directory, kept on the box for two weeks. It's cheap, it's restorable without touching the DO panel, and it means a Tuesday mistake doesn't cost you back to the previous weekend's image. Enough for a throwaway. Production needs off-box copies, retention, and a documented restore, which is the “verified backup and restore plan” item in the proof of concept. Four things need capturing: the database, the files directory (everything uploaded), config.inc.php plus public/ (site logos, journal styles), and plugins/ — because add-ons installed from the Plugin Gallery land there and are not in the tarball, which is otherwise all the application code there is.

Times two, since the OPS install. There are now two applications on this box and they share nothing that matters here — separate databases, separate files directories, separate configs. A backup that names ojs and stops silently omits the whole preprint server, and nothing reports it until a restore is attempted. The script below therefore takes an application name and is called once per app; a third would be one more line. If you installed the earlier OJS-only version, it was called ojs-backup — replace it and update the crontab line, rather than adding a second script beside it.

bash — save as ~/pkp-backup; installed below
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%F)
DEST=/home/forge/backups
mkdir -p "$DEST"

# $1 = app name, which is also the database name and the <app>-files prefix
# $2 = web root under /home/forge, where config.inc.php, public/ and plugins/ live
backup_app() {
  local app=$1 site=$2
  mysqldump --single-transaction --routines --triggers "$app" | gzip > "$DEST/$app-db-$STAMP.sql.gz"
  tar -czf "$DEST/$app-files-$STAMP.tar.gz"  -C /home/forge "$app-files"
  tar -czf "$DEST/$app-config-$STAMP.tar.gz" -C "/home/forge/$site" config.inc.php public plugins
}

backup_app ojs ojs.icjia.cloud
backup_app ops ops.icjia.cloud                 # drop this line only if OPS is actually gone

find "$DEST" -type f -mtime +14 -delete        # two weeks of dailies on dev
bash — install it
sudo install -o root -g root -m 755 ~/pkp-backup /usr/local/bin/pkp-backup   # root-owned, world-executable: the cron job runs as forge, and a root-owned 750 would refuse it
# mysqldump reads ~/.my.cnf, so the password lives in one 600 file, not in the script or crontab:
printf '[client]\nuser=forge\npassword=YOUR_DB_PASSWORD\n' > ~/.my.cnf && chmod 600 ~/.my.cnf
(crontab -l 2>/dev/null; echo '15 3 * * * /usr/local/bin/pkp-backup') | crontab -
/usr/local/bin/pkp-backup && ls -lh /home/forge/backups   # six files: db, files, config × two apps

--single-transaction gives a consistent InnoDB snapshot without locking tables, which is all OJS and OPS use. Together with the weekly DO image you have two independent layers: nightly app-level dumps on the box for the everyday "I broke the journal" case, and the weekly whole-disk image for the "the box is gone" case — bearing in mind that the dumps live on the box and go with it, which R3 spells out. Quarterly, restore a dump into a scratch database (CREATE DATABASE ojs_restore; zcat … | mysql ojs_restore) and untar the files archive somewhere; if both open cleanly, the backup is real.

Check the count, not just the exit code. A good night leaves six files, three per application. The failure worth designing against is not the script erroring — it is the script succeeding while covering only one app. Rehearse the restore against OPS at least every other quarter, precisely because it is the one nobody thinks about.

Handoff

Once both installers have finished, mail is working from each, and the backup script above has run once by hand and left its six files, the rest belongs to the administrators in R&A and happens entirely in a browser. Hand over two admin logins, not one — OJS and OPS keep separate user tables — and point the journal administrator at Running the journal and whoever runs the preprint server at Running the preprint server. Do not walk them through it here; those guides are the single copy and they are kept current.

One thing stays with IDS, and it applies to each application separately. If the Site Administrator role is not offered in the user form when they create a backup admin, it has to be granted directly in that application's database — ojs or ops:

sql — run by IDS, against the right database
USE ojs;   -- or ops
SELECT user_id, username FROM users;
SELECT user_group_id FROM user_groups WHERE context_id = 0 AND role_id = 1;
INSERT INTO user_user_groups (user_id, user_group_id) VALUES (<user_id>, <user_group_id>);

The new administrator logs out and back in to see the Administration menu. A handover without a working backup is a handover of risk, which is why the backup section sits before this one.

Upgrading OJS and OPS

The next real task after install, and the one most likely to be done by someone who did not do the install. Run the upgrade from the command line, not the browser: the CLI is not behind nginx or PHP-FPM, so none of the three timeouts that broke the install apply to it. That single choice removes errors 8 and 9 from the table above.

It is now two upgrades, not one. PKP ships OJS and OPS on the same release train — 3.5.0-5 landed for both on the same day — so a new version almost always means both applications need doing. The steps below are written for OJS; run them again for OPS, substituting ops for ojs throughout (database, files directory, web root, tarball) and downloading the OPS tarball rather than the OJS one. Do them one at a time and verify each before starting the next, so that if the second goes wrong you are debugging one upgrade rather than two.

U1

Back up first, and prove the backup exists

Not the weekly droplet image — an application-level backup you can restore selectively. Run the script from the backups section and look at what it produced before going further. It backs up both applications, which is what you want here: an upgrade that goes wrong on one is a good moment to still have the other.

bash
/usr/local/bin/pkp-backup
ls -lh /home/forge/backups | tail -6          # expect today's date on all six
U2

Read the release notes for the version you are moving to

Check the new release’s docs/README.md and its PHP requirement before anything else. The PHP trap from step D recurs on every upgrade: a release can drop support for the version you are running, or still not support the newest one installed.

bash
php -v                                        # what the CLI will run the upgrade with
php -r 'echo PHP_VERSION, "\n";'

The CLI PHP and the web PHP are different binaries and can be different versions. If the site runs on 8.3 via fastcgi_pass, run the upgrade with php8.3 explicitly, or you will upgrade the database using one version and serve it with another.

U3

Take the site offline, unpack alongside, and keep your state

OJS has no maintenance mode. A one-line return 503; as the first line inside the site's server { } block answers every request with 503 before any location is matched, so nobody submits into a half-upgraded database. (A location / { return 503; } would not do it: the regex PHP location wins over it, and every OJS URL is a PHP URL.)

bash
# 1. Offline: add `return 503;` as the first line inside server { } in the site's nginx file, then
sudo nginx -t && sudo systemctl reload nginx
# 2. On a workstation, not the box (PKP's site refuses the droplet): wget the tarball, scp it to /home/forge/
# 3. On the box:
cd /home/forge
tar -xzf ojs-<new-version>.tar.gz            # unpacks to ojs-<new-version>/
cp ojs.icjia.cloud/config.inc.php ojs-<new-version>/config.inc.php
cp -r ojs.icjia.cloud/public/. ojs-<new-version>/public/
diff -rq ojs.icjia.cloud/plugins ojs-<new-version>/plugins | grep '^Only in ojs.icjia.cloud'   # gallery-installed plugins: not in the tarball
cp -r ojs.icjia.cloud/plugins/<category>/<plugin> ojs-<new-version>/plugins/<category>/       # once per plugin listed above
mv ojs.icjia.cloud ojs.old-$(date +%F) && mv ojs-<new-version> ojs.icjia.cloud

The files directory is outside the web root and is not touched by any of this, which is the point of putting it there. Keep ojs.old-* until the upgrade is verified — it is the fastest rollback there is.

U4

Run the upgrade and clear the caches

bash
cd /home/forge/ojs.icjia.cloud
php8.3 tools/upgrade.php check                # reports the version gap without writing
php8.3 tools/upgrade.php upgrade
rm -rf cache/t_compile/* cache/t_cache/* cache/*.php

The upgrade is not idempotent. If it fails part-way, restore the database from U1 and start again rather than rerunning it over a half-migrated schema.

U5

Remove the 503, then verify

bash
grep -n 'installed' config.inc.php
mysql -u forge -p -e "SELECT major,minor,revision,build FROM ojs.versions WHERE product_type='core' ORDER BY date_installed DESC LIMIT 1;"
# delete the `return 503;` line from the site's nginx file, then
sudo nginx -t && sudo systemctl reload nginx
curl -sI https://ojs.icjia.cloud/index.php/index/login | head -1   # 200

Then load a published article, an editorial queue, and the admin dashboard in a browser before declaring it done. A version row alone does not prove the front end works. If any of that fails, put the 503 back, swap the directories back, and restore the U1 database dump — that is the rollback, and it is why ojs.old-* is still there.

Restoring from backup

A backup nobody has restored is a hypothesis. Do this once now, and once a quarter after, into a scratch database so the real one is never at risk.

The commands below say ojs. Every one of them has an ops twin — same shape, different database, files directory and web root. Substitute throughout, and alternate which application you rehearse against so both get exercised.

R1

Rehearsal: restore into a scratch database

Proves the dump is readable and complete without touching the live site. This is the quarterly test the proof of concept commits IDS to.

bash
mysql -u forge -p -e 'CREATE DATABASE ojs_restore CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;'
zcat /home/forge/backups/ojs-db-<date>.sql.gz | mysql -u forge -p ojs_restore
mysql -u forge -p -e "SELECT COUNT(*) AS submissions FROM ojs_restore.submissions;"
tar -tzf /home/forge/backups/ojs-files-<date>.tar.gz | head       # archive opens and has content
mysql -u forge -p -e 'DROP DATABASE ojs_restore;'
R2

Real restore, on the same box

For “the journal is wrecked but the machine is fine”. Take the site offline first, as in U3. Only the wrecked application needs restoring — the other shares nothing with it and should be left alone.

bash
mysql -u forge -p -e 'DROP DATABASE ojs; CREATE DATABASE ojs CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;'
zcat /home/forge/backups/ojs-db-<date>.sql.gz | mysql -u forge -p ojs
rm -rf /home/forge/ojs-files && tar -xzf /home/forge/backups/ojs-files-<date>.tar.gz -C /home/forge
tar -xzf /home/forge/backups/ojs-config-<date>.tar.gz -C /home/forge/ojs.icjia.cloud
chmod 640 /home/forge/ojs.icjia.cloud/config.inc.php
rm -rf /home/forge/ojs.icjia.cloud/cache/t_compile/* /home/forge/ojs.icjia.cloud/cache/t_cache/*

The database, the files directory and config.inc.php must come from the same backup run. A database expecting a galley file the archive does not contain will show broken downloads that look like a permissions fault.

R3

Whole-machine loss

If the droplet itself is gone, the nightly dumps went with it: they live in /home/forge/backups on that machine and nowhere else, which is the gap production closes with off-box copies. Restore the weekly DigitalOcean image from the control panel (droplet → Backups → Restore). Everything on it, dumps included, is as old as the image — up to a week. If a newer application backup exists anywhere off the box, lay it over the image with R2, once per application; the whole-disk image restores both, and both are equally stale. Afterwards re-check the three things a restored image gets wrong: that nginx is still held (apt-mark showhold), that both sites’ certificates have not expired while the image sat idle, and that the low-memory MySQL setting survived (performance_schema should still be OFF, or the box will swap under two apps).

Next-droplet checklist

  • First thing: top. If mta-sts-daemon is burning CPU, purge postfix-mta-sts-resolver before doing anything else.
  • Then sudo nginx -t. Don't trust the Forge dashboard's green light.
  • apt-mark hold nginx once it's running, because Forge compiles modules against the exact build.
  • Issue the Let's Encrypt cert in Forge before installing the app, so its base URL is https from the start.
  • Set the PHP limits (step D), the nginx body cap (E) and the whole PHP location block with its timeouts and denies (F) by hand, before the installer; verify with the readiness page.
  • Download tarballs on a workstation and scp them up; PKP's site refused the droplet's TLS client.
  • Create the app database as utf8mb4. Put uploaded files outside the web root (e.g. /home/forge/<app>-files).
  • Delete the readiness page. Rotate any credential that touched a chat, ticket, or screenshot.
  • Mail is post-install: confirm the Mailgun domain shows verified with DKIM before config.inc.php exists.
  • After install: chmod 640 config.inc.php, set force_ssl, decide job-runner vs cron.
  • Two apps on 2 GB: performance_schema = OFF for MySQL and disable the unused php8.5-fpm pool; check free -m for swap creep.
  • Install the backup cron and run it once by hand before handing over either admin login. Count the output files — three per application, so six with OJS and OPS both installed.
  • OJS 3.5.0-5 does not run on PHP 8.5. Install 8.3 from the sury PPA by hand (step D) and point fastcgi_pass at it before running the installer.
  • Second application: repeat only the per-site steps (P1–P8) — site and cert, the step F block, its own database and files directory, the installer, [email], its backup line, its own admin. Nothing server-level needs doing twice.
