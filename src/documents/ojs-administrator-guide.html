Running the journal

Everything the OJS administrator does, from first login to publishing an issue — all of it in a web browser.

Last updated4 September 2026

You do not need a server login, and you will not be given one. If a task has a settings screen, it is yours. If it needs someone to log in to the machine itself, it is a ticket.

Before you start

IDS installs the software, connects the database, and hands you an administrator username and password. From that point the journal is yours to run.

This guide is written for the person in R&A administering the journal. It assumes no server knowledge and asks for none. Two companion documents cover the rest: a proof-of-concept overview explaining what OJS is and what adopting it would take, and a server runbook for the developers who build the machine.

While this is a test: nothing you do here is permanent, published, or indexed. Break things freely — that is what a test server is for.

Getting started

Work top to bottom. The whole sequence takes an afternoon, and step 6 is the one that actually answers whether OJS fits how R&A works.

  1. 1

    Log in and secure the admin account

    Sign in with the username and password IDS gave you. First thing: top-right menu → Edit Profile → Password and set your own. Then Profile → Contact and make sure the email is one you actually read; OJS sends every notification there.

  2. 2

    Create the journal

    A fresh OJS site has no journals. Administration → Hosted Journals → Create Journal. Give it a title, a short web path (this becomes part of every link, so keep it short and never change it later), and a language. Everything else can be filled in afterwards.

    OJS then drops you into the journal’s Settings wizard. Fill in Masthead (title, ISSN if you have one, description) and Contact (principal contact is you; technical contact is IDS). Skip the rest for now.

    Leave off during the test: Settings → Distribution → DOIs, and anything labelled indexing or search-engine registration. A DOI cannot be withdrawn once issued, and nothing on a temporary server should carry one. The proof-of-concept overview explains why at length.

  3. 3

    Learn the roles before adding people

    Roles decide what each person can see. Getting them right at the start saves a lot of confused email later.

    RoleWhat they can doWho gets it
    Site AdministratorEverything, on every journal, plus site settings and creating journals.You, and one backup (step 5).
    Journal ManagerAll settings, users, and workflow for one journal. Cannot create journals.Whoever runs the journal day to day — often you.
    EditorSees every submission; assigns reviewers; makes decisions.Editor-in-chief or managing editor.
    Section EditorSame as Editor, but only for submissions assigned to them.Associate editors, topic leads.
    ReviewerSees only the submissions they are invited to review.Anyone who reviews. Can be created when inviting.
    AuthorSubmits and tracks their own manuscripts.Anyone who registers.
    ReaderGets issue-published notifications. No editorial access.Subscribers to announcements.

    One person can hold several roles. For a small shop, one Manager who is also Editor, plus a few Reviewers, is a complete journal.

  4. 4

    Add users

    Inside the journal: Users & Roles → Users → Add User. Name, username, email, and a temporary password. Tick Send the user a welcome email so they get their login — this also proves outgoing mail is working. Assign roles on the same form.

    To change someone’s roles later: same screen, click their name → Edit User. People can also register themselves; Settings → Users & Roles → Site Access controls whether that is allowed and which roles they may pick.

  5. 5

    Create a second site administrator

    One admin account with a forgotten password is the single most common OJS support request. Make a backup admin now, before you need one, and tell IDS the username.

    Create the user as in step 4, then edit them and look for Site Administrator in the roles list. If it is there, tick it and you are done. If the list only offers journal roles, the role has to be granted on the server — file a ticket and IDS will run it. The new admin then logs out and back in to see the Administration menu.

  6. 6

    Run one article all the way through

    This is the real test. Make yourself a second account as an Author with a different email address and submit a fake manuscript. Then, back as the editor: assign a Reviewer (a third account), complete the review as that reviewer, record a decision, copyedit, build an issue, and publish it. Every step sends an email; watch them arrive.

    By the end you will know whether the workflow fits how R&A actually works. That is the question this whole exercise exists to answer.

  7. 7

    Name a backup admin, and tell IDS who it is

    If the main administrator leaves, changes roles, or is out for a month, someone else must already be able to log in with full rights. At least one backup, two is better. If a departure is planned, hand over before they go, not after.

Try it first, or file a ticket?

Most questions about OJS turn out to be questions about a setting, not about the server. This is how to tell the difference.

Try it first

You handle these. Most take five minutes.

  • “How do I make OJS do X?” Almost always a setting. Look in Settings, then search the PKP forum (forum.pkp.sfu.ca) or the OJS user guide. Someone has asked already.
  • A user cannot log in. Use the “forgot password” link, or reset it from Users & Roles.
  • Someone cannot see a submission. Check their role; reviewers and section editors only see what is assigned to them.
  • An email went out with the wrong wording. Templates are editable under Settings → Workflow → Emails.
  • The site looks wrong. Theme and appearance live under Settings → Website.
  • A feature seems to be missing. Many are add-ons you can switch on yourself under Settings → Website → Plugins → Plugin Gallery.

File a ticket

These need IDS. Nothing in the browser will fix them.

  • The site is down, blank, or showing an error instead of OJS. (Check uptime.icjia.app first; it may already know.)
  • No email is sending at all, for anyone, after the check below.
  • Uploads are rejected for being too large when the file is a normal size.
  • A new OJS version is out, or the site says it needs upgrading.
  • You need a second site administrator and the role is not offered in the user form.
  • Something needs to change on the web address, its certificate, or the email setup.
  • You have broken it and want it restored from backup. It happens; that is what a test server is for.

The rule of thumb: if the fix is in a Settings menu, it is yours. If the fix needs someone to log in to the server itself, it is a ticket. When in doubt, spend ten minutes looking before filing.

Quick email check

Do this before filing anything about email. It resolves most reports on its own.

  1. 1

    Log out, click Forgot your password? on the login page, enter your admin email, and wait.

  2. 2

    Give it up to 15 minutes. Some mail arrives fast; some does not. Do not file at minute two.

  3. 3

    Check spam and junk. The state’s mail system tags anything from outside as [EXTERNAL], and OJS mail counts as outside. It is often filtered.

  4. 4

    If it never arrives, say so in the ticket. IDS can check the mail provider’s logs, which show whether the message left our system. Those logs are kept for only five days, so report promptly.

A message the provider shows as delivered can still be held on the state’s side. That is a DoIT question rather than an OJS one, and IDS will route it.

Filing a useful ticket

Please do not email IDS staff directly about OJS. Everything goes through a Freshservice ticket, so the request is tracked and anyone on the team can pick it up.

A useful ticket includes:

  • What you were trying to do, and which screen you were on
  • What happened instead, with the exact wording of any error
  • Whether it affects one person or everyone
  • When it started, and whether anything changed right before
  • A screenshot if there is anything to see

Turnaround on the test server is best-effort; it is not a production system and nothing on it is urgent. A live journal would come with a real support agreement, and that is part of the adoption conversation.

When something breaks

Two places to look before calling IDS. Administration → Administrative Functions → System Information shows versions and settings, which is the first thing a ticket will be asked for. The PKP community forum at forum.pkp.sfu.ca has nearly every question already answered, usually by someone who hit it in the same version.

For server-side problems — site down, no email at all, uploads rejected — it is an IDS issue. For “how do I make OJS do X”, it is almost always a setting.
