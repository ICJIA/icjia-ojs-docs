What a preprint actually is

The word does a lot of work, and it is worth getting right before comparing anything. A preprint is a complete piece of research, written up and made public by its authors, before it has been through peer review — or in place of it. It is not a draft, not a summary, and not a work in progress. It is the finished thing, published early.

Three properties do the work

  • A date stamp that holds up. Posting establishes publicly, and permanently, that this work existed on this date. In fields where two teams can be working the same question, that matters.
  • A permanent identifier. A preprint can carry a DOI of its own, so it can be cited in other people's work — and cited correctly — long before any journal accepts it.
  • Versions, kept. Authors post a revision as a new version. The old one does not disappear; anyone who cited it still finds what they cited. When a journal eventually publishes the work, the preprint points at that final version.

Take those three away and a preprint is just a document on a website. They are the whole reason preprint software exists rather than a folder of PDFs.

OJS and OPS: the same machine, geared differently

These two are not competitors and not really alternatives. They are the same software underneath — the Public Knowledge Project builds both from one shared foundation — set up for two different jobs. Seeing the workflows next to each other makes the difference obvious in a way a feature list does not.

OJS — a journal

Four stages. The finish line is an issue.

  • SubmissionAuthor submits; an editor decides whether it goes forward at all.
  • ReviewReviewers are invited, rounds are run, deadlines chased, names hidden if the journal wants them hidden.
  • CopyeditingLanguage, references and house style, with the author signing off.
  • ProductionFinal files made, then scheduled into an issue and published with the rest of it.

Nothing publishes until there is an issue to publish it into. That is not a limitation to be worked around — it is the definition of a periodical, and it is what OJS is for.

OPS — a preprint server

One stage. The finish line is the post.

  • Submission → ProductionA submission lands directly in the only stage there is. There is no review stage to enter, because there is no review.
  • ModerationA moderator checks that it is in scope and appropriate, tidies up the title, authors and summary, and posts it — or declines it, with a discussion thread if there is anything to say.
  • PostedPublic immediately, with a date stamp, and a new version whenever the authors have one.

PKP is careful about the vocabulary here, and so is this document: OPS posts, it does not publish. The distinction is the entire point. A moderator is not an editor, and screening is not review. The description OPS attaches to everything it publishes says so: every item is labelled a preprint, permanently and by design.

The practical consequence: a preprint server cannot be quietly used as a journal, and a journal cannot be quietly used as a preprint server. The software will let you try; the description of the work that reaches Crossref (the non-profit that registers those permanent numbers), Google Scholar and the library catalogues will say which it is either way.

Where OJS, OPS and the Hub overlap

This is the section that decides the matter, so here it is in one sentence: three of the four do the same job, and only OJS does a different one. The Hub as it runs today, the Hub 2.0 rebuild and OPS are all continuous publishers — work goes public when it is finished, approved by one person. OJS is the odd one out: it gathers reviewed work into issues, on a schedule.

First: Hub 2.0 is not a separate option

A major upgrade to the Hub — but not a different way of publishing

This is the point most easily misread, so it is worth being blunt about. Hub 2.0 does not sit in a third place on this page. It publishes the same three kinds of content, continuously, with the same single approval, under the same name, at the same web addresses. On the questions this page asks, most of its column reads “no change”.

None of which is a criticism — it would be a bad misreading of this page to take it as one. Today's Hub dates from 2019 and has had no security updates since 2022, which makes replacing it the most urgent thing described anywhere on this page. Hub 2.0 is a substantial rebuild: a current, supported platform, materially better security, and new capability throughout, including letting an editor highlight a passage and leave a comment on it — a real improvement on a single yes-or-no approval, though a better conversation rather than peer review.

The point is narrower: on the question this page is about — how ICJIA publishes — today's Hub and Hub 2.0 fall in the same place. Hub 2.0 is a better, safer, more capable version of the same publishing model, which is exactly what it was meant to be. And that is why it settles nothing about OJS or OPS in either direction: whichever Hub is running, the two questions in the next box are answered the same way.

What the three continuous publishers already share

  • All three post individual pieces continuously, each when it is finished, with nothing waiting on anything else.
  • All three put a draft in front of one person who approves it before it goes public — a manager in the Studio, a moderator in OPS.
  • All three keep authors, abstracts, topics and attached files as structured information rather than as prose on a page.
  • All three produce a public, searchable library of ICJIA research that stays put and can be cited.

Four out of four. This is the uncomfortable part and the reason this document exists: OPS is not a strange new category — it is very close to what ICJIA already does, and being close to the incumbent is a far harder position to argue from than being different to it.

Two questions separate all four

Everything else is detail. If you remember nothing else from this page, remember these two.

  • 1. Is the work formally reviewed by outside experts?
    Only OJS. Not today's Hub, not Hub 2.0, not OPS. A manager's approval, a moderator's screening and a comment on a passage are all useful, and none of them is peer review. This is the single thing no version of the Hub can be adjusted into providing without becoming a journal.
  • 2. Is it registered as scholarship? — a permanent identifier, versions that stay citable, and visibility to Google Scholar and citation counts.
    OJS and OPS, yes. Neither version of the Hub. Hub articles are read by tens of thousands of people and are close to invisible to the scholarly record. That is a real ceiling on work the agency has already paid to produce, and Hub 2.0 does not set out to lift it.

There is a third thing, and it runs the other way: only the Hub has readers. 60% of the agency's visitors, 84% of its search traffic, fifteen minutes a visit, and roughly 540 web addresses ranked by Google over six years. Neither OJS nor OPS starts with any of that, and neither can hold a dataset or a dashboard as a publication in its own right. Two of the Hub's three kinds of content do not survive a move to either one.

So where does each fall? The Hub, in both versions, is where ICJIA's research reaches people — and Hub 2.0 is that same job done on a current, secure, more capable platform. OPS is the Hub's shape plus a scholarly record: versions, DOIs, indexing, minus the datasets, dashboards and readers. OJS is the only one that reviews anything, and the only one that produces a periodical.

Can we retire the Hub and just use OJS or OPS?

This is the question behind the question, and it deserves a straight answer rather than a defensive one. The instinct runs: ICJIA maintains a publishing platform it built itself. Off-the-shelf software is maintained by other people. Why not move the research into OJS or OPS and stop maintaining anything?

The short answer: the instinct is sound, and it is aimed at the wrong target. What follows is why — including the parts that favour replacing it.

First, the case for it — put as strongly as it deserves

This is not a straw man. In-house software has a specific and well-known failure mode, and ICJIA is living inside an example of it right now.

  • Usually one person understands it. The people who can confidently change a tool built in-house are the people who wrote it. When they move on, the knowledge goes with them and what remains is a system nobody wants to touch.
  • Nobody patches it on a schedule. The clearest evidence is on this page already: the software behind today's Hub stopped receiving security updates in 2022. That is exactly what the instinct is worried about, and it is not hypothetical.
  • You cannot hire for it. There is no market of people who already know an agency's internal tool, no documentation but your own, and no community to ask.
  • Off-the-shelf outlives its adopters. PKP has been developing OJS since 2001 and maintains it with a community of thousands of journals. Security fixes arrive because other people need them, not because someone here had time.

Any honest version of this document has to concede all four. The question is not whether those risks are real — they are — but whether moving the Research Hub into OJS or OPS actually removes them.

What replacing it would genuinely buy

  • Security maintained by strangers, on a schedule. The single strongest argument, and it is a good one.
  • Documentation you did not have to write, and staff you can actually recruit or contract for.
  • No bespoke application code to review, inherit, or explain to an auditor.
  • The scholarly plumbing comes included. Permanent numbers, registering them with Crossref, letting library catalogues collect the listings, and being readable by Google Scholar are all built in — and every one of them would be real work to add to anything home-grown.

What it would cost

  • Someone else's model of the work. OJS assumes a journal; OPS assumes preprints. Neither assumes articles, datasets and dashboards. You cannot adjust settings your way out of what a piece of software fundamentally is.
  • The customisation trap. Closing that gap means add-ons and private alterations — which is work built in-house again, only now wedged inside somebody else's software and broken afresh by every update. This is the trap people underestimate: bought software plus alterations is frequently worse than building it yourself, because you still own the altered part and you are now tied to a release timetable you do not control.
  • Upgrades stop being optional. An in-house tool changes when ICJIA decides. A major OJS or OPS release is a migration with a deadline attached, because staying behind means losing security support — the very thing the move was meant to fix.
  • Faults become someone else's waiting list. A fault in your own tool is something you fix. A fault in software from outside is a report you file and then wait on — or a private correction you now have to maintain forever.
  • You still run the server — and it is more server, not less. Off-the-shelf is not managed. OJS and OPS are web applications with a database behind them, running on a server somebody has to keep updated, backed up, secured and certified. The sibling server runbook is the honest price list: a long document that exists because the first build hit error after error, and that already needed memory tuning to hold two of these applications on one small server.

What would happen to search traffic?

The largest single risk, and the hardest to undo

The Hub earns 21,500 of the 25,500 visitors Google sends the whole agency each year — 84%. That standing is attached to the web addresses themselves, not to the writing on them, and it took six years to build.

  • Every address would change. OJS and OPS build their own web addresses, in a fixed pattern of their own, and roughly 540 Hub pages would move into it. Google treats a moved page as a new page: found again, judged again, ranked again.
  • Forwarding helps, and does not make it free. An old address can be set to forward permanently to its new one, which carries most of a page's standing across — but only if every single address is mapped correctly and kept forwarding forever, and the climb back is still measured in months. One address missed is one article starting again from nothing.
  • The references you do not control. Those addresses are sitting in citations, syllabi, bookmarks, and other agencies' pages. Redirects protect them only for as long as the redirects are maintained — which is now a permanent obligation, not a one-off task.
  • A different index is not the same index. OJS and OPS would improve visibility in Google Scholar, Crossref and library catalogues, which the Hub barely reaches. That is a genuine gain. But it is a different audience from the one arriving through ordinary web search, and it is much smaller. Trading 84% of the agency's search traffic for scholarly indexing is a trade, not an upgrade.

How would moving the back catalogue actually work?

Mechanically tractable. Structurally, it does not fit

The technical half is the easy half, and worth saying plainly so it is not treated as the obstacle: OJS ships tools for bulk-loading existing content, so importing several hundred articles is a scripting job, not a research project.

The structural half is where it fails, and it fails differently depending on which system you pick:

  • Into OJS, every article needs an issue. There is no way to publish without one. Six years of continuous output would have to be filed into invented retrospective volumes and numbers — a fiction, permanently recorded in the description that travels with each article, about work that was never issued that way.
  • Into OPS, every article becomes a preprint. Not a label you can change: it is what the software is, and it is written into everything OPS emits. ICJIA's finished, authoritative research would be permanently and machine-readably described as provisional. That is not a mismatch; it is a false statement about the work.
  • Datasets stop being publications. In both systems a dataset is a file attached to something else. It can still carry its own DOI — a real strength — but it stops being an entry a reader can find on its own.
  • Dashboards have nowhere to go at all. There is no version of this migration where an interactive dashboard lives in OJS or OPS.

Which produces the decisive practical objection. Because the dashboards cannot move, and the datasets do not survive intact, ICJIA would not be retiring its in-house platform — it would be keeping a reduced one for the content that could not leave, and running a second web application and its database next to it. The stated goal is fewer systems to maintain. The result is more.

One thing to watch while deciding

There is a bias at work here, it runs in both directions, and it is worth naming because it operates quietly and feels like judgement rather than assumption.

The familiar one is “not invented here” — preferring your own tool because it is yours. The one more likely to matter in this decision is its mirror: assuming software that was bought or downloaded is inherently more serious than software built in-house.

That assumption is not reliable. Off-the-shelf software is not automatically more correct, better tested, or cheaper to run by virtue of having come from outside — it is differently maintained, and the sibling runbook is a fair record of what that costs in practice: a long document that exists because a standard installation of standard software hit error after error, on a box that then needed tuning by hand. Meanwhile the Hub's results are not a matter of opinion or advocacy. Sixty per cent of the agency's visitors, 84% of its search traffic, fifteen minutes a visit — those are measurements.

None of which makes the in-house platform above criticism. Its most serious problem is stated plainly several times on this page: the software behind today's Hub has had no security updates since 2022, and that is a real and urgent fault, which is precisely what Hub 2.0 was built to fix.

The fair test is the same test, applied to both: what does it do well, what does it do badly, what does it cost to run, and what happens when it breaks? Applied evenly, it is what the rest of this page has tried to do. Applied unevenly — scrutinising the in-house tool and waving the downloaded one through because it came from outside — it produces a decision that looks rigorous and is not.

So: right instinct, wrong target. The worry — that ICJIA depends on software only ICJIA maintains, and that it stopped being patched in 2022 — is legitimate and urgent. But the fix for it is Hub 2.0, which rebuilds the Hub on a current, supported, mainstream platform and is already built and waiting for a decision. That addresses the security and maintenance problem directly, keeps the readership and the web addresses, and keeps datasets and dashboards as publications. Moving the content into OJS or OPS would address the same problem indirectly, at the price of the agency's search standing, two of its three kinds of content, and an honest description of its own research.

Could the Studio be built out instead?

The previous section asked whether to replace the Hub. This one asks the fair inverse, and it is the more useful question: if the objection to the in-house platform were written down as a list of requirements, could Hub 2.0 and Studio 2.0 be extended to meet them?

Mostly yes — and more cheaply than is generally assumed. One item cannot sensibly be built in-house, one is misattributed to the software entirely, and the rest are ordinary work.

What this estimate is based on, and what it is not

These are rough bands — days, weeks, months — for a developer who already knows the software. They are not quotes, and they are worked out from the public Hub 2.0 and Studio 2.0 previews rather than from the inside, so treat them as an order of magnitude and nothing finer.

Two things about those previews do matter, because they change the answer. The honest counterweight

Everything above is buildable. That is not the same as saying it should be built, and the argument against has real weight:

  • Anything built here is maintained here, permanently. Crossref changes what it expects; Google Scholar changes its rules. A piece of in-house plumbing nobody has looked at in three years is the 2022 problem happening again somewhere new.
  • You cannot schedule the shaking-out. OJS and OPS have had their odd cases found by thousands of other sites over many years. A first attempt here will have faults those found long ago.
  • Adding features does not spread the knowledge. Every addition is one more thing only the same small number of people understand.

Which is why the list matters more than the verdict. Some of these requirements clearly favour buying — peer review is not a close call. Some clearly favour building — the Google Scholar labelling is a small change to machinery the Hub already has, and no purchasing process will ever move faster. And one, DOIs, is not a software decision at all: it is a membership and a permanent institutional commitment that ICJIA must make or not make regardless of which system is running.

So the practical recommendation is a specification, not a preference. “We would rather have off-the-shelf software” cannot be met, tested, or costed — by anyone, including a vendor. “Every article must carry a DOI that resolves in perpetuity; prior versions must remain citable at stable addresses; article pages must carry the labelling Google Scholar reads; the list of articles must be collectable by library catalogues” is a list, and any of the three options — extend the Studio, adopt OJS, adopt OPS — can be scored against it honestly, item by item. On the evidence above, that scoring would not come out one-sided in either direction, which is the strongest argument for doing it properly.

If not instead of the Hub, is OPS worth having alongside it?

Short version of the section above

No — for the same reasons as OJS, and one more

Everything the proof of concept says about OJS replacing the Hub applies here: the datasets and dashboards have nowhere to go, and every one of roughly 540 web addresses would move, at a cost the traffic figures make plain.

OPS adds a reason of its own. It labels every item a preprint in the description that travels with it — that is not a setting, it is what the software is. Publishing ICJIA's finished, authoritative research as preprints would describe the agency's work as provisional when it is not. That is worse than a technical mismatch; it is a factually wrong claim about the work, made permanently and machine-readably.

So is it worth having at all?

Hard to justify on its own

This is the honest answer, and it is not the flattering one. The Hub already does continuous posting, and does it for an audience OPS would have to build from nothing. Running a second continuous-posting system means a second thing to keep patched, backed up, and staffed — in exchange for versioning and indexing that a smaller change to the Studio might also deliver.

Where the argument gets interesting is not publication at all — it is the front half of a journal. If ICJIA ever runs the quarterly the proof of concept describes, there is a real gap between “a working paper exists” and “an issue comes out six months later.” OPS fills exactly that gap: the paper gets posted, dated, versioned and citable straight away, and when the reviewed version appears in the journal, the preprint points at it. That is the job OPS was built for, and the one place it is clearly the right tool rather than a near-duplicate of something ICJIA already owns.

Which makes OPS contingent on the journal, not independent of it. If the quarterly does not happen, the case for OPS largely goes with it.

The recommendation: keep OPS installed for the length of the proof of concept — it costs nothing extra to run and it is the cheapest way to see the workflow honestly. Do not treat it as a separate decision. Decide the journal first; OPS is a sensible companion to a quarterly and hard to defend without one.

What is actually running

Installed 6 September 2026 on the same server as the OJS test, sharing its database system, the software that serves web pages, and its outgoing mail. What is not shared is deliberate: the two applications use overlapping table names, so each has its own database, its own files directory, and its own user accounts.

One consequence worth knowing before anyone is given a login: accounts do not carry across. OJS and OPS keep separate user tables, so whoever administers both needs an account on each, created separately and kept in step by hand. Both send as the same shared administrative address, so mail from the two looks identical to a recipient — which is convenient today and worth revisiting if the two ever need to be managed by different people.

How it was installed

The server runbook carries the full second-site procedure — DNS, the web-server configuration copied from OJS, the separate database, the tarball, and the memory tuning both applications needed once they shared one small server.

How the workflow is run

The administrator guide covers OJS. Most of it transfers: the two share their settings screens, their user management and their email templates. What does not transfer is everything about review and issues — in OPS, none of it is there.

Nothing here is permanent

OPS is on the same temporary server as the journal test, at a temporary address, and it goes when that goes.

Nothing posted to it is a record of anything. No DOIs are registered, no preprint is public, and no ICJIA research has been put on it.

Do not post anything to it you would mind losing.
